## 失败分析

25 条失败任务在已返回 token 总量超过 100000 后、下一次模型请求前停止。此时程序的预算检查会抛出异常，原日志被 MCP 上下文包装为 `ExceptionGroup`。累计用量超过阈值是日志事实，内部 `BudgetExceeded` 类型是根据代码执行路径判断，原始日志没有保存异常组内部类型。

另外 2 条任务只有首次模型请求、没有模型响应：easy 的 `e20241028160303262666` 和 human 的 `h20241029143502525564`。原日志只记录 `ExceptionGroup`，无法进一步确认是网络、服务商还是其他请求问题。未自动重试或排除。

代表案例 `e20241028160248698752`：

- Logistics：2 次模型响应、2 个工具调用，累计 6,440 tokens。
- Activities：6 次模型响应、21 个工具调用，累计 98,344 tokens。
- Activities 最后一次请求的消息历史约 56,070 字符，其工具返回内容合计约 36,081 字符；字符数不是 token 数。
- Logistics 和 Activities 均有交接事件，但 Planner 尚未发起模型请求，总用量已达 104,784。

当前 Agent 保留完整消息历史，交接还携带原始工具证据。每次请求重新发送这些内容，使累计输入用量增长很快。这是下一步上下文管理需要优先验证的原因，尚不能由本次单组试运行证明某个改进一定有效。

100000 阈值在请求前按已返回 usage 检查，不能阻止某一次请求本身把总数推过阈值。27 条任务观测用量达到阈值，其中 25 条失败，另外 2 条已在最后一轮返回计划；不能把“达到阈值”直接等同于“执行失败”。
