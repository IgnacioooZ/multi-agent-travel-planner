# Bad case 根因、工具修复与同组复测

## 两轮为何从 easy 3/4 变成 1/4

对照冻结源码，而不是凭印象判断：`runs/20261107-173701-pilot10-eccad8c8/source/lab/` 与 `runs/20261107-175009-pilot10-7103dc6f/source/lab/` 中，workflow、tools、validation、evaluate 完全相同；agent/config 的差异是单次输出使用服务最大值、取消本地上下文拦截、处理可选阈值及记录请求长度。差异证据保存于 `runs/root-cause-audit/code_comparison.json`。

杭州案例排除随机 tool-call ID 后，前两次响应的函数名/参数一致，第三次（Logistics 第 2 步）研究总结开始不同。两轮温度都为 0，但请求 max_tokens 已不同，后续对话也不是同一条轨迹。现有日志无法进一步分离 max_tokens 改变与服务端非确定性各占多少，不能声称“取消上限必然使准确率下降”，也不能声称“其他业务改过导致下降”。一次四条 easy 的结果不足以估计稳定成功率。

这不是忽略回退的理由：原系统把事实字段的正确性寄托在模型每次重新填写上，研究总结或规划稍有变化就可能产生不同错误。下面有可以独立复现的生成端原因，而非只用“随机性”解释失败。

## 按数据产生位置追查

### 酒店：数据和交接正确，最终活动语义错误

`e20241028160845920703` 的工具行与 Logistics 交接都保留酒店真实单价 329；Planner 第一条也填 329，但后续三条同酒店住宿填 0。`h20241029143447759844` 同样是工具返回 277，Planner 后续四条写 0。

进一步检查时间：这些条目包含入住、午休、回酒店等停留，并不都是新的过夜。模型用 accommodation 表示酒店位置活动，再用零费用避免重复付款；官方契约却把每条 accommodation 当成应有真实单价的住宿。这是规划表示与 benchmark 语义不一致，不能只把全部 0 替换成收费来掩盖问题。原核验仅检查 cost=price*rooms，所以 0=0*rooms 会通过，且没有核对酒店原始单价。

### 市内交通：选用的路段没有实际查询

`e20241028160255878579` 的“南京夫子庙步行街→永和园酒楼”、`h20241029143450090032` 的“重庆云端之眼观景台→重庆江北国际机场”，原 trace 均没有对应 start/end 的 goto 查询。最终计划却填入距离、时长和费用。例如南京写 5 分钟/0.5km，公开工具实际为 10 分钟/约 0.8581km。这里没有工具结果可供 MCP 丢失，是 Planner 填入未经查询的事实；原核验只看段落衔接和费用等式，没有逐段验证事实来源。

### 返程：局部合法，整体依赖不满足，修正反馈又缺少可执行候选

两条 easy 与第一条 medium 的车次都真实，但发车早于实际到站。杭州 17:53 发车、18:39 到站；深圳 18:21 发车、18:46 到站；北京原候选 08:00 发车、13:50 才到站。原模型选择班次与活动安排分离；“到站应早于发车”的反馈重复出现，未强制重新选择班次。城际工具默认查询午夜起所有班次且分页，研究候选可能偏向早班；工具本身没有查错，调用条件与后续决策不足。

### 数量字段：可选 schema 与实际计算要求不一致

最后一条 human 多段出租车缺 cars。数量在官方 schema 中未充分约束，模型省略后无法计算真实总费用。工具应按人数生成票数/车数并记录计算，不依赖模型重复抄写每一段。

### 调用参数与传输

旧批次发现一次 goto 参数 JSON 解析错误，发生在 `_execute_tool()` 解析阶段，尚未执行 MCP 请求；与上述路线事实错误不是同一个原因。酒店原始值已到达交接，新增真实 MCP/direct 对照测试返回一致；目前没有这批错误由传输改值造成的证据。

## 针对性修复

新增 `lab/plan_tool.py` 的 `finalize_plan`，通过 `lab/tools.py` 同时暴露给 Direct/MCP。原有 18 个查询工具不变，加一个本地提交工具，两种 Agent 模式使用同一工具。

- 模型决定实体、班次、时段与交通方式；工具精确查实体和班次，生成真实单价、房型、票数/车数、费用以及采用路段的真实结果。
- 每条实际采用的路线都调用公开 goto；按实际前一位置和结束时间计算路线。到达晚于原活动开始时保留原时长并顺延，开放时间/餐次约束再检查；这会显式改变计划时间，所有 before/after 均记录。
- 城际班次 ID 和时刻来自原记录，不能任意顺延发车；赶不上时返回真实到站时间和同站点的晚班候选，由 Planner 选择或重排活动，不自行换掉用户的班次选择。
- 酒店按真实价格计费；下一早晨同酒店出发占位可移除并记录；同日多条住宿不能作为零费用休息占位，返回明确语义错误让 Planner 重排。该 MVP 契约不覆盖复杂的同日多酒店付费安排。
- 公开 API 的精确查询在组件层取得全量候选，避免用分页的前十个班次代替全部可行班次；不访问私有任务、隐藏约束或参考答案，不改变公开数据。
- `Agent.run()` 在工具成功后直接保存其 plan，不再请求模型复制一遍，从而避免“核验后又改写”。最后一轮仍允许提交工具。普通模型 JSON 不能绕过该提交路径。
- 所有内部查询、所选记录、修改与错误都在 tool_result 中；模型/工具调用数照常计数，另用 grounding_queries 记录提交工具内的逻辑事实读取数量（包含缓存复用，不等于新增模型请求）。

运行时仍有未覆盖的用户意图检查，不是一个保证任意需求成功的完整约束求解器。模型仍可能选错实体、超预算或不按反馈重排，需要独立评分。模型温度与长度配置不变，本轮不再修改评分规则。

## 验证

40 项全量测试通过，包含原有 MCP/预算/协议测试和新增的确定性字段生成、不修改输入、真实晚班候选、酒店出发占位、真实 MCP/direct 一致性测试。新增统计字段的 CLI 测试也已通过。

对上一批十份原计划做离线工具重放，保存于 `runs/finalizer-regression/`，不调用模型、不用这组结果冒充新模型实验。其中原南京失败计划由工具修正四处字段后，独立官方评分完整通过；原成都成功计划无改动且仍完整通过。原返程冲突被明确拒绝并提供真实后续车次。相同草案与数据的工具输出可重复一致。

## 冻结版本真实复测

相同 UID 的 4 easy + 3 medium + 3 human；每条一次，multi + MCP，累计 token/本地上下文不设限，单次使用服务最大值。实验目录 `runs/20261107-181314-pilot10-1bc40ec6/`，源码/数据/评分器冻结在 manifest 中。中间版本结果为 easy 3/4、medium 1/3、human 1/3，共 5/10；该版本另有一次 APIConnectionError、提交阶段未收尾以及一次天数错误。未覆盖或替换这批结果。


## 第二次修复：控制流程与公开需求绑定

第一批日志进一步证明，原收尾只收窄工具列表但仍使用 tool_choice=auto；模型在最后一轮继续生成历史中的查询工具名，没有调用提交工具，于是结束轮次而无最终计划。这是编排阶段的完成条件未落实。

最终版本把 Planner 最后四轮保留给提交工具；请求明确指定 finalize_plan，并按 DeepSeek 接口要求在该提交阶段关闭 thinking。前面的研究阶段不变。真实接口预检确认该指定方式受支持（399 tokens，保存在 runs/forced-tool-preflight.json）。

公开请求由 Agent 运行时注入，覆盖模型自己填写的 request；工具只对能明确识别的“玩一天/旅行三天”等表述及数字预算做绑定检查。覆盖范围有限，不声称已实现完整中文意图解析。一次 APIConnectionError/APITimeoutError 可显式重试，任务内最多一次，新增 model_request 事件并计入总次数；SDK 隐式重试仍为 0。

44 项测试通过，新增了提交工具请求参数、公开需求绑定、连接重试计数验证。最终实验开始后没有再改生成、工具或评分代码。

## 收尾核对与边界

case_analysis.json 核对源码、数据、评分器哈希与调用用量，最终 source_data_and_usage_verified=true。ownership_audit.json 确认每份正式计划与成功提交工具的结果完全相同；每次提交工具绑定的 request 与任务原始公开请求一致。

剩余两项分别是预算/时间的联合规划没有收敛，以及餐厅重复规则漏校验，本报告没有将其算成成功。事实生成与任务全局可行性是不同职责；此次改动解决了已定位的事实填写和提交控制问题，并未证明系统任意需求均正确。后续应为这两个剩余问题单独增加机制和对照，不继续在同一冻结批次中修改或替换结果。

新增组合工具与提示词、提交编排均有变化，不应把这些成绩解释为多智能体架构本身的优势；后续 single/multi 必须都使用相同工具和预算。
