# 重构后的代码阅读顺序

这次重构突出正常执行主线，不改变三个角色的职责、提示词、轮次上限、交接内容或评分规则。命令和输出文件格式保持兼容。

## 先读 Agent.run()

在 `lab/agent.py` 搜索 `async def run`。主流程分三步：

1. `response = await self.model.complete(...)`：模型读取消息历史，提出工具调用或回答。
2. `if not response["tool_calls"]`：模型不再调用工具，返回当前角色的回答与证据。
3. `for call in response["tool_calls"]`：逐个执行本次响应提出的调用，将结果加入 `messages`，然后进入下一轮模型请求。

`run()` 中另一处 `if` 是开头的角色工具筛选。无需先读完全部检查，才能理解循环。

下方只有三个辅助方法：

- `_prepare_request()`：检查共享预算和上下文长度；最后一轮收起工具；记录即将发起的模型请求。
- `_record_response()`：累计 token 用量，写日志，将模型消息加入历史。
- `_execute_tool()`：检查本轮允许的工具、剩余调用次数和 JSON 参数，执行工具并返回参数与结果。

方法名开头的 `_` 是 Python 的惯例，表示供类内部使用，不是另一种框架或新协议。

## 再读 workflow.solve()

`lab/workflow.py` 中按执行顺序展开：

1. 划分交通住宿、景点餐饮角色的工具范围。
2. 创建 `logistics_agent`，运行并得到 `logistics`。
3. 创建 `activities_agent`，将交通住宿结果一并传入，得到 `activities`。
4. 将两份交接内容与官方 `output_schema` 交给 `planner`。
5. 解析 Planner 返回的 JSON。

单 Agent 模式跳过两个研究角色，直接进入规划阶段。没有改成并行或动态 Supervisor。

## CLI 按职责阅读

- `main()`：根据命令选择一条分支。
- `run()`：准备实验、逐条运行任务、汇总统计，并关闭模型客户端。
- `run_task()`：一个任务连接工具、调用 `solve()`、保存计划和执行指标。
- `build_parser()`：声明命令和参数，不执行工作流。
- `doctor()`、`show_tools()`、`call_one()`、`smoke()`：各自独立的辅助命令。

## 哪些检查删掉或合并了

- 删除 `run()` 中重复读取密钥的调用。创建 `DeepSeekModel` 时仍然检查密钥，并且先于写入实验目录。
- `allowed` 直接从本轮 `active_tools` 提取；空列表得到空集合，因此执行时无需再额外检查 `not active_tools`。
- 单 Agent 模式不再额外获取一遍只供两个研究角色划分权限的工具列表。
- 工具执行的多层 `if/elif/else/try/else` 改为拒绝后直接返回，正常执行路径放在方法末尾。

## 哪些检查需要保留

- 模型次数、工具次数、已观察到的 token 用量和上下文长度限制。
- 每次实际工具调用前的预算检查：同一次模型响应可以提出多个调用。
- 工具权限、非法 JSON 和参数不是对象的检查：这些输入由模型生成，不能假设始终正确。
- MCP 的结构化结果、文本错误兼容和 `isError` 处理：错误结果不能算成功。
- 批量任务异常记录与连接清理：失败任务必须留在评测分母内。

没有加入新的框架、自动重试或自动修复。总行数因拆行和职责说明有所增加，主循环的分支与嵌套减少。
