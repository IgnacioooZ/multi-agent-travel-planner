## 第 1 页 · Motivation（一）多智能体协作的进展

- **眉标**：01 · Motivation
- **标题**：多智能体协作已在复杂任务上取得显著进展
- **引言**：随着大语言模型（LLM）能力的提升，越来越多的系统不再依赖单个模型，而是将任务分解给多个角色 agent，通过分工与对话协作完成目标。多智能体系统已在软件工程、科学研究、推理与行为模拟等方向上展现出单模型难以企及的能力。以下是几类代表性的主流工作。

| 类别 | 代表工作 | 作用 |
|---|---|---|
| 协作框架 | AutoGen · MetaGPT · ChatDev · CAMEL | 将任务分解给多个角色 agent，通过对话与分工完成软件开发、科学研究等复杂流程。 |
| 推理增强 | Du et al., 2023 | 多智能体辩论：多个 agent 相互质疑与修正，提升事实性与推理正确性。 |
| 行为模拟 | Park et al., 2023 | Generative Agents：多 agent 环境中涌现出可信的社会行为。 |

- **收束**：这些系统的能力来源是「**角色分工 + 协作**」。但现有工作大多在**整体效果**上报告提升，很少把「协作」这一变量单独、受控地评估——我们难以判断：提升究竟来自协作本身，还是仅仅来自更多的模型调用与计算预算。

## 第 2 页 · Motivation（二）为什么选旅行规划

- **眉标**：02 · Motivation
- **标题**：旅行规划是评估协作的理想试验场

旅行规划是一项典型的复杂决策任务，天然适合检验多智能体协作，原因如下：

1. **任务天然可分解。** 一次完整的旅行规划涉及交通、住宿、景点、餐饮等多个子目标，每个子目标对应不同的查询工具与约束。这种结构很适合把任务拆给多个角色分别研究。
2. **约束可验证。** 预算、时间、开放时间、距离可行性等都是**硬约束**——「成功」可以被客观判定，而不是靠"看起来合理"。这让我们能用统一的评分器衡量协作是否真的有效。
3. **公开基准与沙盒。** ChinaTravel 提供固定任务集、受控数据库快照与离线评分器，支持可复现评测；每个任务只暴露公开的 uid 与 request，隐藏约束仅由评分器使用，避免了"看了答案再答"的泄漏。
4. **现有不足。** 少有工作在与单智能体**相同的模型、工具、预算**下做受控对照，协作的收益难以归因——这正是我们想填补的空缺。

- **收束**：因此，我们复现一个多智能体旅行助手，搭建 single / multi 受控对照，以**评估并进一步改进协作机制**。

## 第 3 页 · 研究问题与贡献

- **眉标**：03 · 问题与贡献
- **标题**：研究问题
- **问题**：在**相同的模型、工具与预算**下，多智能体协作能否在旅行规划任务上带来**可靠性提升**？这种提升与**任务复杂度、推理成本**的关系如何？
- **展开**：我们希望证明多智能体是有用的——具体而言，在简单的 easy 任务上，单智能体可能更省；但在**复杂的 medium / human 任务**（多意图、条件 / 依赖预订、长对话）上，多智能体应展现出明显的优越性。

| 贡献 | 标题 | 内容 |
|---|---|---|
| 1 · 系统 | 可复现的评测底座 | MCP 接入 19 个工具，独立评分器检查 schema、常识与硬约束，全程离线可复现。 |
| 2 · 方法 | 受控对照流程 | single / multi 共用模型、工具、任务与总预算，指标对齐：通过率、tokens、调用数、耗时。 |
| 3 · 发现 | 复杂任务上的优越性 | multi 在 medium / human 上优于 single；easy 上两者相当，但 single 更省成本。 |
| 4 · 定位 | 可归因的评估 | 用数据回答「协作是否值得」，为后续协作机制改进提供基线。 |

## 第 5 页 · 工具与 MCP

- **眉标**：05 · 工具与 MCP
- **标题**：19 个工具，按领域分组

系统通过 MCP（Model Context Protocol）向 agent 暴露 19 个工具，覆盖旅行规划的完整信息获取链路：

| 领域 | 数量 | 工具 |
|---|---|---|
| 景点 | 5 | attractions_keys · attractions_select · attractions_id_is_open · attractions_nearby · attractions_types |
| 住宿 | 3 | accommodations_keys · accommodations_select · accommodations_nearby |
| 餐饮 | 6 | restaurants_keys · restaurants_select · restaurants_id_is_open · restaurants_nearby · restaurants_with_recommended_food · restaurants_cuisine |
| 交通辅助 | 4 | intercity_transport_select · goto · poi_lat_lon_search · next_page |
| 提交 | 1 | finalize_plan |

- **finalize_plan（事实化提交工具）**：由沙盒生成真实价格、班次与衔接时间，返回修改记录与冲突信息——不让模型再次复制事实字段，从源头避免"抄错价格 / 时间"这类事实性错误。
- **MCP 实现**：MCP server 以 stdio 子进程运行，任务开始自动启动、结束自动清理；工具查询 benchmark 沙盒，不执行真实订票或付款。

## 第 6 页 · 评测设置（含示例）

- **眉标**：06 · 评测设置
- **标题**：受控的评测设定

| 维度 | 设定 |
|---|---|
| 数据 | ChinaTravel：easy 300 · medium 150 · human 154（共 604 条）；固定 10 条开发集 + 20 条留出集；Agent 仅拿到公开 uid 与 request。 |
| 评分 | 独立逐任务评分：schema + 常识约束 + 硬约束 全过才算通过；缺失计划计入失败（执行完成 ≠ 评分通过）。 |
| 预算 | 每任务最多 24 次模型请求、60 次工具调用；累计 token 不设限，单次输出取服务上限。single / multi 一致。 |

### 一个具体例子：输入 → 输出 → 评分

- **输入（agent 只看到这个）**：`当前位置上海。我一个人想去杭州玩一天，预算1500人民币，请给我一个旅行规划。`

- **这个 plan 的实际结果**：当日往返（06:10 出发 → 19:25 返沪），全程总费用约 **550.7 元**（由评分器逐项累加），在 1500 预算内。

## 第 8 页 · 结果（二）成本视角：easy 上 single 更省

## 第 9 页 · 失败分析与优化方向

- **眉标**：09 · 失败分析
- **标题**：两类失败 → 指向协作改进方向

multi 的失败主要集中在**跨多步推理的联合约束**问题（以下为占位示例）：

| # | 失败 | 现象 | 类别 |
|---|---|---|---|
| 1 | 预算 / 时间联合规划未收敛 | 只满足预算或时间其一，未能同时满足。 | 联合约束 |
| 2 | 重复餐厅规则漏检 | 多步查询中丢失「不重复餐厅」的约束。 | 约束漏检 |

- **分析**：两条失败都不是**工具或协议**问题，而是多个约束需要在**跨角色、跨多步**的推理中被同时守住时，出现了丢失或未收敛。
- **对比 single**：single 的失败多为**预算耗尽**（ExceptionGroup）——单 agent 在复杂任务上上下文膨胀到超过请求 / 工具预算；multi 的失败多为约束不收敛，两者是不同性质的失败（占位）。
- **未来优化方向**（针对这两类问题的机制改进）：
  1. **显式依赖与执行条件**：把「预算 ≤ 1500」和「时间可行」写成显式约束，提交前逐条校验；
  2. **条件执行**：预订动作显式依赖"可用性查询成功 + 满足价格条件"；
  3. **带界重试的校验步**：提交前增加验证步骤，失败时有限次数地回修；
  4. **结构化交接**：角色间用结构化、保留来源的证据交接，减少约束丢失。

## 第 10 页 · 结论

- **眉标**：10 · 结论
- **标题**：协作的收益随任务难度上升

1. **复杂任务上 multi 更可靠。** medium / human 上 multi 明显优于 single（86% vs 60%、90% vs 68%）；single 的失败多为预算耗尽，multi 靠角色分工保持在预算内——多智能体协作是有用的。
2. **easy 上 single 更省。** 简单任务两者准确率相同，但 single 更省（约 2.75× tokens、约 3× 延迟之差），说明简单任务无需协作。
3. **成本—收益权衡成立。** multi 用更高的推理成本换来了 medium / human 上更高的通过率，这是可接受的代价。
4. **边界（诚实声明）。** 本页结论基于**占位**数据（每难度 50 条），待实测替换；仍需重复运行与留出集验证。
